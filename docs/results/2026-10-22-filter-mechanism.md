# Cairnwork 延後驗收擋錯能力量測結果（2026-10-22）

本報告為 Cairnwork 延後驗收機制的偵測器評估（detector evaluation），屬方向性結果。在測試題組中，真實模型犯的錯僅有 7 份修補，其中擋下 5 份，因此目前不對真實模型錯誤的擋下率下結論；針對人工破壞 Issue 描述行為的規則式突變，延後驗收擋下了 205/205；真實模型的正確修補被誤擋為 0/83；同時需明確指出，「驗收通過不等於沒有缺陷」，通過驗收的變更仍可能帶有隱藏測試未涵蓋的缺陷。

## 我們測什麼

本輪評估旨在量測 Cairnwork 的交付前延後驗收機制（部署 commit `ceeed7e` 之 `cairnwork-verify`：採用獨立驗收帳號、隔離沙盒、單次使用測試 commit，執行延後 F2P 與 P2P 測試）在面對錯誤修補時的攔截能力，以及對正確修補的誤擋情況。

真值基準（Ground Truth）由外部開源 Python 專案的上游篩選測試搭配全套件回歸比對構成，與延後驗收各自在乾淨 clone 環境中獨立執行。評估樣本共 430 份修補，涵蓋三種來源：

- **參考解**（89 份）：外部開源 Python 專案的官方或標準修正，真值全數為正確修補（0 錯／89 對），用於評估基準誤擋。
- **規則式突變**（252 份）：針對修補引入規則式的人工破壞，使其偏離 Issue 所要求的規格，真值包含 205 份錯誤與 47 份正確修補，用於檢驗擋錯能力。
- **Haiku 實跑**（89 份）：由單一模型在題目組中生成的實際修補，真值包含 6 份錯誤與 83 份正確修補。

評估方案與門檻於開跑前凍結於 `2026-10-22-cairnwork-filter-mechanism-prereg.md`（方案 2）。指標包含擋錯率（附單側 95% Wilson 下界）與誤擋率（附單側 95% Wilson 上界）。若真實錯誤樣本數小於 20，依預註冊標註為資訊不足，不逕行下結論。

## 結果

| 來源 | 份數 | 真值 錯／對 | 擋錯率 | 誤擋率 | 預註冊參考門檻 |
|---|---|---|---|---|---|
| 參考解 | 89 | 0／89 | — | 1/89＝1.1%（≤4.9%） | — |
| 規則式突變 | 252 | 205／47 | 205/205＝100%（≥98.7%） | 7/47＝14.9%（≤25.3%） | **誤擋未達** |
| Haiku 實跑 | 89 | 6／83 | 5/6（資訊不足，<20） | 0/83（≤3.2%） | 擋錯：資訊不足 |
| 合計 | 430 | 211／219 | 210/211＝99.5%（≥97.9%） | 8/219＝3.65%（≤6.4%） | 合計主要由突變撐起，不單獨引用 |

- **攔截原因**：延後驗收所擋下的修補，其原因全數為測試失敗（FAILED_TESTS），無 REFUSED、ERROR 或 TIMEOUT。
- **攔截機制分布**：在擋下的錯誤中，僅依賴延後 F2P 擋下 109 份、F2P 與 P2P 共同擋下 93 份、僅依賴 P2P 擋下 3 份，另有 5 份判定原因不明（Core 判定失敗但日誌未記錄失敗細節，研判為驗收過程遭遇逾時）。
- **依錯誤類型分析**：僅破壞篩選測試者擋下 62/62；僅造成既有回歸者擋下 23/23；兩者皆破壞者擋下 125/126。
- **敏感度檢驗**：在具備 holdout 測試作為真值的樣本中，holdout 判錯的 46/46 全數被延後驗收擋下；holdout 判對者有 3/60 被擋；兩種真值判定在 101/106 份中保持一致。

## 怎麼解讀

1. **針對「改壞了 Issue 描述的行為」，延後驗收表現高度可靠**：規則式突變幾乎全屬此類破壞，延後驗收達成了 205/205（100%）的攔截率。
2. **真實模型的錯誤：只有 7 份，擋下 5 份**：在測試題組中全部 7 份真實錯誤（Haiku 實跑 6 份加上前期測試補查的 1 份）中，延後驗收擋下 5 份，漏擋 2 份。這 2 份漏擋的情況不同，樣本只有 2 份，不做推論：其中一例（Haiku 實跑）通過了延後測試，但弄壞了共用基底類別的另一個子類測試，而目前的 P2P 規則僅納入「檔名對應被修改模組或直接 import 該模組」的測試檔，這個鄰近類別的回歸沒被挑進驗收範圍；另一例（第一輪補查）是 Issue 範圍內的邊界情況，延後測試沒有涵蓋到，holdout 的 F2P 變體才抓到。兩次漏擋分別指向兩個可改處：P2P 範圍太窄（追蹤修復中），以及延後測試對 Issue 內邊界情況的涵蓋不足。總結而言，真實錯誤樣本僅 7 份，樣本過小，尚不足以對真實錯誤擋下率下結論。
3. **誤擋分析**：真實模型的正確修補完全未被誤擋（0/83）；規則式突變出現 7 份誤擋，大多是由於上游真值測試覆蓋不完全所致（在具備 holdout 的 2 份中 holdout 亦判定為錯誤），預註冊已將此列為已知限制；參考解的 1 份誤擋為 Cairnwork 在多個驗收同時排隊時遭遇的偶發性失敗（重跑兩次皆判定為 VERIFIED），非測試內容問題。
4. **小問題上模型基準錯誤率本來就低**：Haiku 在 89 題中僅出現 6 次錯誤，這顯示交付前驗收在小型修補上的核心價值在於提供安全保險，而非顯著拉高成功率。

## 執行紀錄

- 本次執行依據預註冊文件 `2026-10-22-cairnwork-filter-mechanism-prereg.md`（方案 2），數據經獨立重算核對，各項格位數據與單側 95% Wilson 信賴區間界限均一致。
- **測試 harness 更新（abbc8f6）**：執行過程中，因特定突變修補導致測試程式卡死，觸發 900 秒全域逾時並造成真值評估中斷。隨後 harness 調整為「逾時直接判定該修補失敗」，並設定真值階段之 pytest 執行上限為 300 秒。此項調整僅涉及真值階段的異常處理機制，延後驗收端與待測修補本身未受影響；後續執行均記錄每階段 harness HEAD。
- **驗收併發調整**：因驗收帳號配置獨佔鎖限制，實際執行併發數為 1，未採用原預註冊規劃之最高併發 3。
- **日誌保存**：Haiku 實跑的 worker 原始日誌因檔名衝突發生覆寫，但每列對應的 token 用量、成本與輪數資訊皆完整保留。
- **已知限制照實揭露**：規則式突變為人工構造的錯誤模式；真值測試存在漏測可能；worker 與 Cairnwork 共用 uid（屬工具層邊界限制）；本次評估僅涵蓋單一真實模型。

## 下一步

依據本次量測的具體數據與現象，後續預計推進以下改進：

- **擴大 P2P 測試涵蓋**：將 P2P 的挑選規則由「檔名對應」擴大至「被修改模組的整個測試子目錄」或「全套件中基準全數通過的測試」，以捕捉跨模組與共用基底類別的回歸錯誤（雖會增加驗收耗時，但能涵蓋前述漏擋的真實錯誤情況，此項為追蹤中的修復）。
- **修復排隊偶發失敗**：排查多個驗收並行排隊時出現的驗收失敗異常（CORE_FAILED_VERIFICATION）。
- **解除沙盒與環境限制**：
  - 修正倉庫根目錄之 `.py` 模組一律被視為受保護輸入而遭到拒絕的問題。
  - 改善沙盒環境限制，補足對 POSIX semaphore 的支援，使依賴 multiprocessing 的 Python 專案得以順利進行驗收。
